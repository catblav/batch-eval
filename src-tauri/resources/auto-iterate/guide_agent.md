# 提示词自动迭代脚本 · 使用说明

这份文档是写给 AI agent 的操作手册。用户会把工作目录交给你，让你跑测试、改提示词。

脚本负责：调用被测模型、调用裁判模型、按数据集逐条判分、和上一版对比、存档。
你负责：读文件、定参数、改提示词、把结果讲清楚。

脚本只用 Python 标准库，不需要装依赖，Python 3.8 以上即可。

---

## 一、开场：只说这两件事

用户刚把文件夹交给你、还没配环境时，开场就照下面这样说。说完就停，等用户回复；不要继续追问运行方式，也不要提前预告后面要问什么。

> 好的，我来带你使用这个评测台，并自动评测数据和改进提示词。现在只需要你做两件事：
>
> **1. 配置 API**
>
> 打开「黑猫-自动评测台」→ ① API 配置，两张卡：
> - 被测模型：你要评测的提示词跑在哪个模型上。Base URL 填接口地址，模型名照接口文档填，API Key 粘进去。
> - 评测模型（裁判）：负责判分。被测模型配好后点「同步到评测模型」可以复用同一套。
>
> 每张卡可以先点「测试连接」确认能通；点「测速」会发 3 次短请求，给出实际延迟和 tok/s——跑得慢是接口的事还是评测台的事，一眼能看出来。确认没问题点「保存配置」。
>
> **2. 放三个文件**
>
> 把这三样放进同一个文件夹：<这里填用户给的工作目录>
> - 被测提示词（system prompt）
> - 评测提示词（裁判用的判定标准）
> - 数据集（CSV 或 Excel，一行一条）
>
> 文件名随意，能看出是什么就行。放好告诉我，我来读文件、跑测试。

### 用户回复之后，按顺序做

**1. 确认 API 真的配好了。** 默认配置目录下的 `settings.json` 里，target / judge 都有 baseUrl 和 model。没配好就再提示一次，不要问运行方式。**不要向用户索要 API key 原文，也不要自己去写 `settings.json`。**

**2. 读文件，分清角色。** 哪个是被测提示词、哪个是评测提示词、数据集有哪些列。分不清直接问用户，不要猜。

**3. 用参数把文件指给脚本。** 这三样都不需要导入评测台：

| 要什么 | 怎么传给脚本 |
| --- | --- |
| 被测提示词 | `--prompt-target <文件>` |
| 裁判提示词 | `--prompt-judge <文件>`（`评测提示词/` 下只有一份时可省略） |
| 数据集 | `--dataset <文件>`（csv / json / xlsx） |
| 用户消息模板 | `--user-template <文件或文本>`，不传就用评测台里存的 |

用户消息模板按数据集的列拼，例如列是「原文、风格」：

```bash
--user-template "{{原文}}\n\n{{风格}}"
```

不确定列名就先跑 `--list`，它会打印列名、条数和每行内容。

**4. 确认数据读到了。**

```bash
python 脚本/脚本_提示词自动迭代.py --dataset <文件> --list
```

条数或内容不对，先解决数据，不要往下跑。

**5. 开跑前再问三个问题**，并且等用户回答：

- 先跑一次测评数据，还是开始迭代改进？
- 如果迭代，最多几轮？
- 要不要输出完整结果文件（含每条输入与模型输出）？

不要提前预告这几个问题，也不要在配置阶段就问；不要替用户决定，不要拿脚本默认值直接开跑。

## 二、目录结构

工作目录下通常是：

```
<工作目录>/
├─ 说明文档/自动迭代_说明.md
├─ 脚本/脚本_提示词自动迭代.py
├─ 评测提示词/    裁判提示词（迭代对象）
├─ 评测数据/      数据集（csv / json / xlsx）
├─ 评测输出/      完整结果、被测输出缓存、审计日志
└─ 提示词历史/    裁判提示词的历史版本
```

被测提示词放在工作目录哪里都行，用 `--prompt-target` 指过去。这些目录只是默认约定，不满足时全部可以用参数指过去。状态文件 `regression_state.json` 放在工作目录根。

脚本唯一假定的是模板变量关系：

- `{{input}}`：裁判看到的输入 = 被测提示词 + 本条输入
- `{{output}}`：被测模型对这一条的实际输出

除此之外脚本一无所知：数据集有哪些列、裁判用什么格式表示通过与否，都要你先读文件、再决定。

## 三、确认配置能用

两条路，按存在情况选：

**A. 用「黑猫-自动评测台」里已经配好的**

默认读取应用配置目录下的 `settings.json`：

| 系统 | 路径 |
| --- | --- |
| Windows | `%APPDATA%\com.batcheval.app\settings.json` |
| macOS | `~/Library/Application Support/com.batcheval.app/settings.json` |
| Linux | `~/.config/com.batcheval.app/settings.json` |

这条路上脚本以只读方式读配置，不会改它。里面的 apiKey 是明文，**不要打印、不要复制到任何文件或日志里**。

- 这条路上，被测提示词和用户消息模板默认取应用里保存的值；跑文件夹流程时，用 `--prompt-target` / `--user-template` 覆盖。
- 只支持 OpenAI 兼容接口。应用里如果选的是 anthropic 原生协议，脚本会直接报错，需要先换成 OpenAI 兼容入口。
- 配置读不到就停下来，让用户先在评测台里把 API 配好，不要自己编一份配置。

**B. 用独立的 config.json**

```json
{
  "target": {
    "baseUrl": "https://.../v1/chat/completions",
    "apiKey": "${TARGET_API_KEY}",
    "model": "...",
    "temperature": 0.7,
    "maxTokens": 4096,
    "timeoutSecs": 120
  },
  "judge": {
    "baseUrl": "https://.../v1/chat/completions",
    "apiKey": "${JUDGE_API_KEY}",
    "model": "...",
    "temperature": 0,
    "maxTokens": 4096,
    "timeoutSecs": 120
  },
  "userTemplate": "{{列名}}"
}
```

密钥建议写 `${环境变量名}`，脚本会自动展开。`userTemplate` 必填，用数据集的列名写。可选字段：`topP`、`extraBody`、`extraHeaders`（后两个是 JSON 字符串）。

接口走 OpenAI 兼容的 `/chat/completions`。

## 四、确认数据集读到了

```bash
python 脚本/脚本_提示词自动迭代.py --dataset <文件> --list
```

输出会先给列名和条数，再逐条列内容。看三件事：列名对不对、条数对不对、内容有没有乱码。

- 不传 `--dataset` 时，应用里存过数据集就优先用它；没有才去 评测数据/ 找唯一的一份。说不清读的是哪份，就明确传。
- `--list` 也需要 API 配置可用，会先加载配置再列数据。

条数或内容不对，先解决数据，不要往下跑。

Windows 上如果终端输出是乱码，命令前加 `PYTHONIOENCODING=utf-8`（PowerShell：`$env:PYTHONIOENCODING="utf-8"`），再读一次。

## 五、读裁判提示词，决定怎么取判定结果

脚本不认识裁判的输出格式，**你必须先读裁判提示词，找到它约定的输出格式，再显式指定提取方式**。不指定会直接报错退出，没有默认值。

先找出裁判提示词：用 `--prompt-judge` 指过去；不指时默认取 评测提示词/ 下唯一一份 `.md` / `.txt`。

然后按它的输出格式二选一：

**裁判输出 JSON**

```bash
--pass-field pass
```

- `--pass-field KEY`：这个字段的值为真即通过。布尔值、`"true"` / `"yes"` / `"通过"` / `"合格"` 都识别为真。
- `--type-field KEY`：错误类型字段（可选）。
- `--reason-field KEY`：判定理由字段（可选，不填则把裁判原始回复存为理由）。

字段名必须来自裁判提示词里真实写的那份输出契约，不要猜。

**裁判输出纯文本**

```bash
--pass-regex "判定：通过"    # 命中即通过，未命中即不通过
--fail-regex "不通过"        # 命中即不通过，未命中即通过
```

只给一个时按上面对应的规则跑；两个都给时，先看 fail 再看 pass。

`--pass-field` 与 `--pass-regex` / `--fail-regex` 只能二选一。

## 六、运行

文件名、模板里的列名都按你实际读到的替换。

**单次运行（先跑一遍测评数据）**

```bash
python 脚本/脚本_提示词自动迭代.py \
  --prompt-target 被测提示词.md \
  --prompt-judge 裁判提示词.md \
  --dataset 数据集.xlsx \
  --user-template "{{原文}}\n\n{{风格}}" \
  --mode single \
  --pass-field pass --type-field errorType --reason-field details \
  --yes
```

跑一遍全量，输出完整结果文件，不比较基线、不消耗轮次。

**迭代运行**

```bash
python 脚本/脚本_提示词自动迭代.py \
  --prompt-target 被测提示词.md \
  --prompt-judge 裁判提示词.md \
  --dataset 数据集.xlsx \
  --user-template "{{原文}}\n\n{{风格}}" \
  --mode iterate \
  --round-limit 5 \
  --pass-field pass --type-field errorType --reason-field details \
  --yes
```

评测台里已经存过用户消息模板时，`--user-template` 可以不传。

迭代模式做四件事：

1. 第一次跑没有基线，这一轮的结果直接成为基线。
2. 之后每次跑，拿「上一轮通过的条目」和这次对比，上次过、这次没过 = 回归。
3. 每轮开始前检查轮次上限；到达上限会拒绝继续，要强行继续得加 `--accept` 或调大 `--round-limit`。
4. 基线建立后，数据集、被测提示词、用户消息模板只要有一处变了，会拒绝运行（退出码 4），避免把「换了输入」误判成「改坏了提示词」。确认是有意更换，优先 `--reset` 清空状态重建基线；要保留历史就加 `--accept-input-change`，它只放行这一次，不影响本轮验收判定。

**迭代改的是裁判提示词**，也就是 评测提示词/ 下那份文件。被测提示词和数据集不动。

**迭代的循环：**

1. 跑一轮全量 iterate。
2. 看未通过的条目和裁判给的理由。
3. 改裁判提示词文件里对应的判定规则，保存。
4. 再跑同一条命令。脚本每次读文件的当前内容，并把这一版归档。
5. 重复，直到采纳或到轮次上限。

**基线什么时候变、轮次怎么算：**

- 基线只在「采纳」时更新。拒绝采纳的那一轮基线不动，接着改、接着跑就行。
- 每跑一次全量 iterate，轮次 +1，不论采纳与否。
- `--accept` 是强制采纳 / 强制继续，会把拒绝的结果也当采纳并覆盖基线，只在用户明确要求时用。

**定位单条**

```bash
python 脚本/脚本_提示词自动迭代.py --mode iterate --only 3,7 ... --yes
```

`--only` 只跑指定序号，不计轮次、不比较基线、不更新基线，适合改完针对某个失败用例验证一下。

**其他开关**

- `--full-output` / `--no-full-output`：是否写完整结果 CSV。
- `--rerun-target`：强制重跑被测模型。
- `--adversarial-file cases.json`：对抗样本，迭代模式下额外统计拦截率。格式：`[{"name": "用例名", "content": "原文", "output": "模型输出"}]`。
- `--target 3,7`：指定目标序号，任意一条不通过则本次验收不通过（退出码 5）。

`--yes` 表示非交互，不会弹任何提问；agent 调用时必须带 `--mode` 和 `--yes`，否则交互提问会阻塞。

## 七、结果怎么看

**终端输出**

```
通过 8 / 9，未判定 0
============================================================
验收结论：拒绝采纳
  - 有回归：[6]
```

- **未判定**：裁判的回复里取不出「通过 / 不通过」（格式不合约、调用失败）。这类不能算通过，也不能算不通过，建议用 `--only` 重跑那几条，或检查 `--pass-field` / `--pass-regex` 是否设对。
- **回归**：上一轮通过、这一轮没通过的序号。
- **验收结论**：没有回归、没有目标未达成、没有未判定，才是「采纳」。

**退出码**

| 码 | 含义 |
| --- | --- |
| 0 | 通过 / 采纳 |
| 1 | 有回归 |
| 2 | 超出轮次上限 |
| 3 | 对抗样本拦截率下降 |
| 4 | 输入（数据集 / 被测提示词 / 用户模板）被改动 |
| 5 | 目标序号未达成 |
| 6 | 有未判定条目，需要重跑 |

单次模式不看通过率：只要跑完且没有未判定就返回 0，有未通过的用例也是 0。通过情况看终端输出或结果 CSV。

**产物**

- `评测输出/result_<时间戳>.csv`：序号、输入、被测输出、结果、错误类型、判定理由。只保留最近 5 份，更早的自动清理。
- `评测输出/regression_log.csv`：每轮的审计日志。
- `评测输出/target_outputs.json`：被测输出缓存。数据集、被测提示词、用户消息模板、被测模型的调用参数（模型名、温度等）都没变时直接复用，改裁判提示词不会重跑被测模型。需要强制重跑加 `--rerun-target`。
- `提示词历史/<时间>_<哈希>.md`：裁判提示词的历史版本。每轮把本轮使用的版本归档，内容与上一份相同就不重复存。回滚就是找到上一轮的存档文件。

**存档与回滚**

```bash
python 脚本/脚本_提示词自动迭代.py --history
python 脚本/脚本_提示词自动迭代.py --restore <存档 ID>
```

`--restore` 只打印回滚命令，不会自动覆盖文件，确认后再执行。

## 八、每次跑完，向用户汇报这些

1. 通过数 / 总数，未判定数。
2. 验收结论：采纳还是拒绝，原因是什么。
3. 没通过的条目：序号、输入摘要、裁判给的理由（引用裁判原文，不要自己改写）。
4. 下一步建议：改哪一句、再跑哪几条验证。

不要只报一个通过率就完事。

---

## 九、不要做的事

- 不要修改测试数据去迁就提示词。
- 不要为了让用例通过去改被测提示词——那是被测对象，不是评测标准的调节阀。
- 不要放宽裁判提示词的标准来凑通过率。
- 不要猜 `--pass-field` / `--pass-regex`，先读裁判提示词。
- 不要打印、复制、写日志任何 API key。
- 不要删除 提示词历史/ 里的存档。

用户要的是「这次改动有没有把原来能过的弄坏」，不是「想办法让数字变好看」。
